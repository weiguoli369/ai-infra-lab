# Lab 001：输入长度与 Prefill / Decode

状态：Planned · 阶段：S1 · 尚无代码和实验结果 · GitHub Issue：待创建。

## 研究问题

在模型和生成配置相同的情况下，输入长度如何影响首段响应延迟和整体请求耗时？哪些观测能够支持 Prefill/Decode 的解释，哪些还需要服务端证据？

初始假设：输入长度改变会影响输入处理工作量，但客户端延迟还受排队、缓存、网络、代理缓冲与输出行为影响。实验不要求长输入一定更慢。

## 启动前确认

- 服务地址与模型标识；此前对话出现过 `ds`，实际可用性待核实。
- GPU 型号、显存、服务端引擎与版本；无权限读取的项明确标注未知。
- 是否可获取 Tokenizer、usage、服务端指标和缓存配置。
- 是否独立实验服务，允许的并发、时长与停止阈值。
- 推理/思考模式、Chat Template、最大上下文及输出限制。

## 第一轮实验设计

1. 先发送一次请求，检查流式内容、错误处理、超时与计时起点。
2. 若可使用匹配的 Tokenizer，构造约 128/512/2048 输入 Token 的三组样本；包含模板后的实际长度另记。否则记录实际文本与字符数，并将 Token 长度标为未知。
3. 固定模型版本、任务、采样与输出上限；记录实际输出长度、提前停止和 reasoning 内容。输出长度未匹配时，不用总耗时差直接推断 Decode 性能。
4. 以并发 1 开始；预热后每组至少重复五次，交替/随机运行顺序。记录缓存状态，重复前缀可能命中缓存，不与冷缓存结果混用。
5. 采集请求开始、首个内容块、结束时间、usage、状态/错误与运行配置。服务端可观测时再关联排队与引擎指标。
6. 比较原始样本、中位数与波动，绘制输入长度—延迟图，列出下一轮需要排除的混杂因素。

预设 128/512/2048 是目标档位，按模型窗口和服务约束调整；不以字符数冒充 Token 数。

## 指标边界

第一轮主要测客户端首段内容延迟与端到端耗时。明确定义首段是否包含 reasoning；流式块可能合并 Token，因此暂不据此计算精确 TPOT/ITL。客户端首段延迟不等于纯 Prefill GPU 时间。
