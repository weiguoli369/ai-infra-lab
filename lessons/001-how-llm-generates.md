# 第一课：大模型怎样从输入走到输出

这份文档供你独立阅读、思考和复述。建议分两次学习：第一次读第 1～6 节，第二次读第 7～10 节并完成练习。总共可以安排 45～60 分钟，也可以按自己的节奏拆开。

本课讨论常见的 **Decoder-only、自回归文本模型**，例如常规使用方式下的 Qwen、Llama。先理解单个请求、普通逐 Token 生成与 KV Cache；推测解码、多模态和并发调度留到之后。

读完后，你应当能够解释：输入如何变成模型处理的数据，Prefill 与 Decode 各自在做什么，KV Cache 为什么存在，以及“响应慢”有哪些不同含义。

本课的学习成果是你自己的解释、图和问题记录。实验工具在理解这些概念之后再使用。

## 1. 从一个实际现象开始

假设你向模型发送一句话：

> 请解释一下 GPU 为什么适合并行计算。

你可能会观察到：发送之后先等了一段时间，然后文字开始出现；文字出现后，又持续输出了一会儿。

这段过程至少有两个值得分别观察的部分：**开始输出前的等待**，以及**开始输出后的生成**。

先在纸上写下你的初始判断：等待时，系统可能在做什么？文字出现后，系统又可能在做什么？现在的答案可以不准确，读完再回来修改。

你过去排查网络或系统故障时，可能会把“访问慢”拆成 DNS、建连、服务处理和数据传输。研究推理性能也需要拆解过程，而“模型响应慢”这个描述本身还不足以定位原因。

## 2. 模型实际接收的是什么

### 2.1 从文字到 Token ID

用户输入的是文字，模型计算使用的是数值。中间由 Tokenizer 将文本切分、编码成 Token ID。

Token 可以对应一个词、词的一部分、一个汉字、标点，或其他片段。同一段文本在不同 Tokenizer 下可能得到不同数量的 Token。因此，字符数和 Token 数需要分开记录。

例如，可以用下面的示意理解这个转换：

```text
一段文字 → 若干 Token → 一串整数 ID
```

这里没有给出真实切分或 ID。具体结果必须用所选模型的 Tokenizer 查看，不能靠中文字符数猜测。[阅读依据：Hugging Face Tokenization algorithms](https://huggingface.co/docs/transformers/tokenizer_summary)

### 2.2 为什么输入不一定只有你键入的那句话

聊天服务通常还会把系统提示、历史对话、角色边界等组织成模型使用的输入格式。你只键入一句话，实际送入模型的上下文可能还包含多轮历史。

因此，分析输入长度时，要考虑最终送入模型的完整序列，而不只是输入框里的新增文字。

### 2.3 从 ID 到模型计算

Token ID 是编号，本身不是含义。模型首先通过 Embedding 将编号映射为向量，再经过多层计算，形成可用于预测下一个 Token 的表示。

你可以把向量先理解为一组数值，把模型层理解为对这些数值进行变换的计算。这里暂时不展开矩阵维度和 Attention 公式；下一阶段会用实际形状解释它们。

**停下来想一想：**为什么“输入 100 个汉字”和“输入 100 个 Token”不能当作同一个实验条件？

## 3. 生成回答为什么通常要一步一步进行

自回归生成的基本过程是：根据当前已有的序列，预测下一个 Token；选出这个 Token 后，把它接入序列，再预测下一个。

为避免真实分词带来的干扰，我们用抽象 Token 演示。假设输入是三个 Token：

```text
A B C
```

第一轮模型根据 `A B C` 的上下文，得到下一位置的候选分数，再按生成策略选出 `D`。第二轮的上下文是 `A B C D`，模型选出 `E`；接着利用 `A B C D E` 选出 `F`。

```text
已有 A B C       → 选出 D
已有 A B C D     → 选出 E
已有 A B C D E   → 选出 F
```

“选出”值得单独理解。模型先给候选 Token 打分，生成策略再决定取哪个：可以选择高分候选，也可以按概率采样。因此，同一输入可能因生成配置不同得到不同输出。

第二个新 Token 的计算依赖第一个已经选出的新 Token。普通自回归路径因此存在顺序依赖；单步内部仍然有大量可在 GPU 上并行执行的数值计算。

这个循环在达到输出长度限制、生成结束标记或满足其他停止条件时结束。[阅读依据：NVIDIA 对推理过程的说明](https://developer.nvidia.com/blog/mastering-llm-techniques-inference-optimization/)

**自我检查：**“逐 Token 生成”和“GPU 并行计算”为什么可以同时成立？尝试分别从生成步骤之间和一个步骤内部解释。

## 4. Prefill：处理已经知道的输入

在开始回答前，输入序列已经给定。模型需要处理这些输入，在各层计算中建立上下文状态。这个处理输入的阶段通常称为 Prefill。

输入位置全部已知，让模型能够在每层组织多个位置的并行计算。但因果关系仍然存在：某个位置只能利用允许它看到的上下文，不能读取未来位置。输入位置可并行处理，不代表模型各层都能同时执行。

在常见的生成路径中，处理完输入后，可以利用最后输入位置的预测结果选择**第一个新 Token**。所以，“Prefill 只处理输入，完全不参与首个输出的产生”会把边界理解得过于机械。

回到 `A B C` 的例子：Prefill 处理 `A B C`，然后选择 `D`。这次计算还会留下后续可以复用的中间状态。

这里的“处理输入”不会修改模型权重。模型加载、普通推理和训练是不同的工作：加载准备权重，推理使用权重，训练通常涉及计算并更新参数。不要把一次请求的 Prefill 理解为临时重新训练模型。

**停下来写一句话：**模型在 Prefill 中获得的“这次请求的上下文状态”，与加载好的“模型权重”，有什么不同？

## 5. Decode：利用上下文继续生成

第一个新 Token `D` 已经选出。为了预测下一个 Token `E`，模型处理 `D`，同时利用先前上下文留下的信息。之后处理 `E`，再预测 `F`。

后续这种逐步扩展输出的过程通常称为 Decode。下面把“本轮新处理的输入”和“本轮选出的输出”分开：

| 步骤 | 本轮新处理的 Token | 本轮选出的新 Token |
|---|---|---|
| Prefill | A、B、C | D |
| 第一次后续 Decode | D | E |
| 第二次后续 Decode | E | F |

这个表格容易混淆的地方是：**刚选出的 Token，要进入后续一次计算，才会形成它自己的相应上下文状态。**选出 `D`，与把 `D` 送入模型计算，是相邻但不同的动作。

同一个模型因此会面对两类工作：一次处理已有的较长输入，以及反复处理新位置并利用历史。两者的计算组织和资源使用可能不同。

先把这种差异理解成一个需要测量的问题。输入规模、并发、模型结构、精度和硬件都会改变表现，不要直接把“某阶段总是受某种瓶颈限制”当作结论。

**自我检查：**如果输入有四个 Token，输出要生成三个 Token，在这里的普通路径下，哪些 Token 参与 Prefill？后续两次 Decode 分别新处理哪个 Token？自己画出过程。

## 6. KV Cache：保存哪些可以复用的信息

上述过程有一个自然的问题：预测 `E` 时还需要历史上下文，怎样避免每次都从头计算历史？

在因果 Attention 中，可以保存先前位置在各层已经得到的 Key 和 Value，后续计算再复用。保存这些数值张量的缓存就是 KV Cache。它不是完整回答或原始文字的副本。

在我们的例子中，Prefill 后保存了 `A B C` 的相应 KV。后续处理 `D` 时，会利用旧 KV，并加入 `D` 的 KV，然后预测 `E`。历史信息仍参与计算，只是其中可复用的部分不用重复生成。

缓存以占用内存换取复用，随上下文扩展而增长。具体增长方式与模型和缓存实现有关。[阅读依据：Hugging Face How caching works](https://huggingface.co/docs/transformers/main/en/cache_explanation)

现在可以把模型权重和请求状态分开想象：同一个模型处理不同请求时使用同一套已加载权重，而请求中的 Token 历史不同，其缓存状态也不同。某些服务还能跨请求复用相同前缀，这属于之后研究的 Prefix Cache。

**写下你的解释：**“有 KV Cache 后，生成新 Token 就不需要历史上下文了。”这句话有什么问题？用两三句话说明。

读到这里可以暂停。合上文档，用 `A B C → D E F` 把第 3～6 节复述一次，标记自己解释不顺的地方。

## 7. 把模型计算放回完整请求链路

用户等待的时间，还包括模型执行之外的部分。一个简化的在线服务链路是：

```text
请求发出
  → 网络与网关
  → 输入准备与服务排队
  → 引擎调度
  → Prefill 与首 Token 选择
  → 后续 Decode
  → 结果经过网络，逐步到达用户
```

这是逻辑分解，不是固定的进程图。实际系统可能合并环节、交错调度多个请求，也可能通过缓存跳过部分重复工作。

可以用三个观测点描述用户体验：

- `t0`：客户端开始发出请求。
- `t1`：客户端收到第一个输出 Token。
- `tN`：客户端收到最后一个输出 Token。

**TTFT（Time To First Token）**描述开始到首个输出的等待。在上述口径下是 `t1 − t0`。它包含哪些环节，取决于你在哪里计时。

**TPOT（Time Per Output Token）**描述首 Token 之后的平均生成间隔。若有 N 个输出 Token 且 N > 1，同一客户端观测口径下可以计算：

```text
TPOT = (tN − t1) / (N − 1)
```

例如，只有一个输出 Token 时就没有“后续间隔”。最终完成消息还可能晚于最后一个 Token，完整请求耗时也需要单独定义。

vLLM 提供首 Token、排队、推理及输出间隔等指标，阅读时应确认每个指标的具体起止点。[阅读依据：vLLM Production Metrics](https://docs.vllm.ai/en/latest/usage/metrics/)

### 两个需要分清的观测口径

**直接在 Colab 调用模型：**可以从输入准备好、调用生成前开始，记录 Token ID 可用的时间。该值包括框架执行、采样和数据拷贝等开销。

**通过 HTTP 接口调用服务：**通常观察到的是一个个流式内容块。一个块可能合并多个 Token，也可能只有角色或控制信息；首个内容块到达时间不能自动当作首 Token 精确时刻。

两种实验都有学习价值，但测量范围不同。它们也都不能仅凭客户端时间就给出纯 GPU Prefill 耗时。

**停下来想一想：**同一模型，直接本地调用和经过网关调用，首段等待不同。你需要增加哪些证据，才能解释差异？

## 8. 为什么要分别改变输入长度和输出长度

理解阶段差异之后，实验设计才有依据。

如果改变输入长度，同时又让模型输出完全不同长度的回答，那么完整耗时的变化可能来自输入处理，也可能来自多生成了很多 Token。两个因素混在一起，就很难回答原本的问题。

所以，研究输入长度时，应尽量固定模型、生成配置、输出长度与运行环境，并记录实际输入和输出 Token 数。即使做到了这些，预热、缓存状态和其他工作负载仍可能影响结果，需要重复观察。

接着可以研究另一个问题：保持输入条件近似一致，改变输出长度，完整耗时又如何变化？这样逐渐把输入处理和逐步生成对用户等待的影响拆开。

“控制变量”不是让每次时间完全相同，而是减少会干扰解释的因素，并诚实记录剩余的不确定性。
